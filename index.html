Case study · 01

Near Wheels

A multi-sided mobility marketplace for India's road-transport and agri-services economy.

Next.jsTypeScriptPrismaPostgreSQLGeminiRazorpay

The problem

Local transport and agri-services in India are fragmented across phone calls, WhatsApp groups, and offline providers. Customers need one place to compare and book; providers need a dashboard, a pricing path, and a payout flow.

The approach

Build a multi-sided marketplace around one auth system, one booking engine, one payment layer, and one admin panel. Seven verticals share the core: ride-sharing, vehicle rentals, garages, driving schools, drone spraying, farm services, and intercity buses. AI is used where it changes the experience — a natural-language budget trip planner.

Engineering challenges

  • Concurrency-safe booking. Booking creation runs inside a transaction with a SELECT … FOR UPDATE row lock, so the second request loses cleanly instead of double-booking.
  • Idempotent payments. Razorpay webhooks replay, so settlement is idempotent, the captured amount is checked against the backend-computed total, and a refund only marks REFUNDED after the gateway accepts it.
  • Authorization that survives demotion. Admin routes revalidate role and user status against the database on every request.
  • Spoof-resistant rate limiting. The client IP is read from the rightmost x-forwarded-for entry, not the leftmost value an attacker can fake.
  • Upload validation. Files are checked by magic bytes, then re-encoded to WebP with sharp and a graceful fallback.

What I built

Full-stack design and implementation: schema, 73 API route handlers, auth, payments, provider/admin dashboards, the Gemini trip planner, 79 Vitest tests, and deployment configuration for Vercel, Docker, and Cloud Run.

StatusPrivate build

79 tests passing. Screenshots captured from the running app.

Scale73 route handlers

BookLoop India

A credit-based book exchange marketplace for Indian readers.

The problem

Readers accumulate books they will not re-read, but resale is friction-heavy and cash pricing makes swaps awkward. A credit system can make exchange feel fair without turning every transaction into a negotiation.

The approach

Build a mobile-first marketplace around a credit ledger: list a book, request a book, reserve credits when an owner accepts, confirm handover, then move credits. The database — not the UI — enforces the rules.

Engineering challenges

  • Atomic exchange. Credits are reserved with row locks when an owner accepts, so concurrent requests cannot overspend a wallet.
  • RLS and grants. Supabase RLS policies protect profiles and listings; public column grants omit owner auth IDs.
  • Lifecycle correctness. Rejection releases nothing because nothing was reserved; cancellation after acceptance releases the hold; disputes freeze the exchange for admin review.
  • Discovery and SEO. Catalogue filters, city/category pages, thin-page noindex rules, sitemap generation, and structured data for books.

What I built

The MVP end-to-end: migrations, RLS, server actions, auth, catalogue UI, wish lists, reviews, moderation, SEO, and deployment documentation.

Not connected to a live Supabase project or deployment yet. The honest boundary is documented.

Open Competitor Lens

An evidence-backed research library where every claim must trace to a retrieved source.

The problem

Most AI competitive-analysis tools produce fluent prose with decorative citations. The model states a price or growth rate, and the linked page says nothing of the sort. The number still reads as authoritative.

The approach

Design against that failure mode: a claim may only appear in a report if a retrieved page contains it, and the quote attached to it appears verbatim in that page's stored text. Evidence records, a fact checker, and a quality gate enforce the rule.

Engineering decisions

  • Deterministic assembly. Comparison, opportunity, evidence, report, and fact-check stages make zero model calls. A quality stage that asks a model to judge its own output is a model agreeing with itself.
  • Retrieval you can inspect. A BM25 lexical index runs offline and deterministically; Chroma provides a persistent vector backend with per-company collections and score inversion handled correctly.
  • SSRF as a first-class concern. Per-hop URL validation, browser route guards, blocked private ranges, and credential redaction in logs and error bodies.
  • Tests as documentation. 1,124 tests, including a 133-case AST test that fails the build on a backwards dependency import.

What is built — and what is not

The analysis library and its test suite are complete. The orchestrator, HTTP API, CLI, GraphRAG modules, and Docker image are not built yet. The repository is a public pre-alpha, and the README says so plainly.

StatusPublic · pre-alpha

Case study · 05

Multi-Agent Market Intelligence

A CrewAI + Gemini pipeline that turns a company name into a structured competitive brief.

agent.run()orchestrating
Plannerscope + keywords
Researchersearch + extract
Analystcompare + verify

The problem

Market and competitor research is repetitive, fragmented, and easy to turn into a chat transcript nobody can use. Teams need a structured brief with clear sections and a review path.

The approach

Split the work into specialist roles. A planner scopes the industry and keywords; a researcher finds competitors; a data agent extracts structured facts; an analyst looks for patterns; a writer produces strict JSON. Shared memory carries context, and a critique loop feeds corrections into the next run.

Engineering decisions

  • Structured outputs over free text. Pydantic schemas enforce the shape of research, campaign, visual, and quality-review outputs.
  • Explicit state. Task states cover pending, processing, completed, approved, rejected, and published — with human review in the loop.
  • Graceful degradation. Optional ScrapeGraphAI extraction falls back to direct generation when the provider is unavailable.
  • One dashboard. A Streamlit surface shows agent progress and the final brief instead of hiding the pipeline in a terminal.

What I built

The agent roles and tasks, the CrewAI orchestration, structured output schemas, the shared-memory and critique loop, and the dashboard. This is a local lab, not a public production service.

StatusPrivate lab

Working locally. No public deployment.

Core ideaSpecialists + review

Each agent has one job; a human can approve or reject the output.
